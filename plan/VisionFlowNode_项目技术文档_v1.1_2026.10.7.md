## 一、项目是什么

**VisionFlowNode**（工程目录 `E:\opencv_python_3_8\PySide\VisionFlowNoed`，名字里少一个 `d`）是一个**节点式机器视觉软件**：
用户在画布上把功能方框连成一条数据流（采集 → 处理 → 检测 → 输出），软件按拓扑顺序执行，并把结果显示/保存下来。
布局与交互刻意对标**海康 VisionMaster**。

> **目标原话（用户）**："我想要做的是像海康 vision master 软件一样的数据流引擎。"
> **"影响必须由算子声明"（用户定稿的引擎语义）**：节点之间的影响只有两条正规通道 —— **声明的图像源绑定** 与 **ROI 继承**；
> **"数据流可视化 → 半自动跟随 → 带角度位置修正"** 是后续要走的演进路线（见第九节）。

## 三、架构总览

### 3.1 分层

```
界面层   main.ui / LineParamsDialog.ui / SetCameraID.ui
         main.py(MainWindow) ── FlowPages(多页签) ── FlowChart(画布/节点/连线)
                              ── ImageGraphicsView(显示) ── ImageGalleryWidget(图库+工具栏)
                              ── 参数窗口：GenericProcessDialog / LineParamsDialog / Circle / Gray
引擎层   main.py 内的：拓扑排序 · 图像源绑定 · ROI 继承 · 节点执行 · 渲染层合成 · 参数归档 · 结果缓存
契约层   NodeRegistry.py：NodeSpec（name/kind/run/draw/format_result/whole_image_param/param_specs）
算子层   ProcessOps(处理 6) · SourceOps(采集 3) · OutputOps(输出 1) · 检测 2（注册在 NodeRegistry）
算法层   Detector.py：直线 / 圆（Hough）
```

### 3.2 节点契约（`NodeSpec`）与四类 kind

| kind | 含义 | 改数据层图像？ | 现有算子 |
|---|---|---|---|
| `process` | 处理：图像被改写，下游看得见 | ✅ | 灰度、取反、滤波、二值化、形态学、边缘提取 |
| `detect` | 检测：图像原样透传，只产出结果数据 | ❌ | 直线、圆 |
| `source` | 流程起点：自己造图 | ✅（是"新图"） | 图片源、视频源、相机源 |
| `sink` | 输出：图像原样透传，把结果写到外部（磁盘） | ❌ | 输出图像 |

两个派生属性是全工程的关键判据：
- **`modifies_image`** = `kind in (process, source)`：多上游"自动挑图像源"时，用它挑**真正改图**的那一支（否则中间的 sink 会冒充"最后一个改图节点"）。
- **`is_flow_level`** = `kind in (source, sink)`：这类节点的参数是**流程级配置**，**不按图片归档**（否则换图会把输出目录/文件名/视频路径清空）。

### 3.3 加一个算子需要动什么（这就是这套架构的价值）

1. 在对应分类模块里写一个算法方法（处理类）或 `run(detector, img, roi, params)`（其它类）；
2. 在同一模块的 `*_SPECS` 里加一条声明（**参数表就是界面**——`GenericProcessDialog` 会照着自动生成"运行参数"页）；
3. 在 `NodeRegistry.py` 末尾的分类注册里被自动收编；需要的话在 `main.py` 的树里加一项（`main.ui`）。

**不用写界面、不用改引擎**（除非引入新的参数控件类型或新的执行语义）。

## 四、核心机制（含"为什么这么设计"）

### 4.1 数据层与渲染层分离（引擎的第一原则）

- **数据层**：`run()` 产出的图像 + 结果数据，在节点之间传递；
- **渲染层**：`draw()` 把结果画到**显示图的副本**上，供人看。

**为什么**：检测类算子的库函数（`cv2.HoughLinesP` 的绘制版）习惯"就地画线"，一旦画在数据层上，下游就会"看见绿线"——
那是**显示用的涂鸦**，不是图像内容。所以：检测类 `run()` 一律 `return img`（同一个对象）、`draw()` 只画显示层；
`NodeRegistry._run_line/_run_circle` 给算法的是 **ROI 的 `.copy()`**（把库函数的副作用丢在副本上）。

**副作用（2026.10.7 实测踩到）**：正因为检测结果只在渲染层，"输出图像"如果只存数据层，**文件里就没有任何检测内容** ⇒
于是有了 `save_content = 数据层图像 / 带检测叠加`（见 4.9）。

### 4.2 影响只能靠"声明的通道"

节点之间的影响**只有两条**：
1. **图像源绑定**（`input_source`）：自动 / 指定上游节点 / 全局图像源 —— 决定"这个节点从哪份图开始算"；
2. **ROI 继承**（`roi_inherit` + `roi_source` + `roi_margin`）：决定"处理哪一块"。

**为什么**：避免"隐式全局状态"式的耦合（否则任何算子都可能悄悄影响别的算子）。好处是可预测、可序列化（方案文件只存这两条通道就够）。

### 4.3 执行语义

| 语义 | 定义 |
|---|---|
| **执行顺序** | 按连线做 **拓扑排序**（Kahn）；孤立节点/环内节点**不执行**，日志如实提示 |
| **连续执行** | 从起点按顺序执行，**执行到"当前选中节点"为止**（`stop_at` 由入口显式传入） |
| **单步执行** | **只执行选中的那一个节点**；输入 = 沿图像源绑定追到起点的那张图 |
| **执行范围** | 图库工具栏下拉框：`运行全部`（对每张图都跑一遍）/ `运行选中`（只跑当前图） |
| **停止** | 急停批量执行 + 停自动播放 + **收尾正在录制的视频** |

**为什么"连续执行要截断到选中节点"**（用户 2026.10.7 拍板）：画面本来就是"点哪个节点就显示执行到那个节点为止"的结果，
如果执行还跑到底，就会出现"我选中的是前面的二值化，结果末尾的输出节点偷偷存了文件"——
**执行范围必须和画面一致**。旧行为（跑到底）已被改掉，受影响的 3 套老用例同步改了断言。

### 4.4 ROI 继承

`_resolve_roi()` 的优先级：
1. 勾了"继承上游" → `继承自=上游ROI框` 用上游**实际用的框**；`=上游结果框` 用上游**结果的外接框**（`result_bbox()`）；
2. 首选拿不到就自动换另一种（并在日志里说明）；
3. 都没有 → 用本节点自己画的 ROI；
4. 最后统一 **外扩 `roi_margin`** 并裁进图像范围。

日志会写 `← 继承上游ROI框` / `← 继承上游结果框` / `← 继承未生效（改用本节点 ROI）`——**让"继承到没继承到"看得见**。

### 4.5 参数归档：按图片，但"流程级节点"除外

- 每个节点的参数在内存里**按"图片标识"存多份**（切图时存档 + 载入）⇒ 一套流程可套用多张图，各图参数独立；
- **例外**：`is_flow_level`（起点节点 + 输出节点）**不归档**。判据写在契约里，引擎和参数窗口都读它。
- ⚠️ 实现细节坑：`_load_node_params()` 是**先 `params.clear()` 再载入**，所以流程级节点**必须跳过**，否则换一次图就把输出目录清空。

### 4.6 三种"键"（最容易被搞混的地方）

| 键 | 组成 | 用途 |
|---|---|---|
| **图片标识** `_image_key_of` | 文件路径（跨会话稳定）；视频帧 = `路径#帧号`；无路径才退化成 `id(对象)` | 参数存档 / 结果缓存 / 缩放记录 |
| **结果缓存键** | （图片标识, 页面 key, 执行方式） | 单步与连续分开、按页分开；只在内存；**相机帧不写缓存** |
| **画面键** | 普通图 = 文件路径；视频 = `video:路径`（**整段共用**）；相机 = `camera:编号` | 缩放/平移状态。视频整段共用是必须的：否则每帧都当成新图、缩放复位，播放时画面"一跳一跳" |

### 4.7 方案持久化（`.vfproj`）

- JSON / UTF-8 / 缩进 2；结构：`format / version / saved_at / current_page / last_source / pages[]`；
- **一个文件装一页**（用户口径）；"导入项目"把文件里的页**追加**到现有页后面（现有页一律保留）；
- **内容指纹去重**：`_page_fingerprint`（工作区）与 `_model_page_fingerprint`（文件模型）**结构必须完全一致**，指纹相同的页跳过（所以两个函数是刻意重复实现的）；
- **先解析 + 校验、全部通过才碰界面**：坏文件不会把界面搞成半成品（失败返回 False，界面保持原样）；
- 节点字段：`id / name / x / y / input_source / params / params_by_image`（漏了最后一个就会"存了读不回来"）。

### 4.8 图像源与图库

- **两类来源并存**：图库（主窗口当前图 + 列表）与**起点节点**（图片源/视频源/相机源）；
- `_flow_source_frame()`：主窗口当前图优先，其次问起点节点，都没有才提示"请先导入图片/视频"；
- 图片源节点与图库**双向同步**：点缩略图 → 同步"图片源"节点路径；删图库条目 → 清相关节点路径（并记进 `_removed_paths`，防止又被自动加回来）。

### 4.9 输出节点（批次4 目标3-M5）

- **参数**：输出目录（**必须每次手填**）/ 输出文件名（默认 = 输入图片名）/ **输出类型**（自动·图片序列·视频文件）/ 图片格式 / 视频格式 / 视频帧率 / **保存内容**（数据层图像·**带检测叠加**）/ 重名策略（**自动编号**）；
- **"自动"档**：图片源 ⇒ 图片序列；视频源/相机源 ⇒ **视频文件**（用户口径："输入是视频就存视频、是摄像头就存视频"）；
- **"带检测叠加"怎么来的**：检测类不改数据层 ⇒ 主窗口在执行到输出节点那一刻，用 `_render_display(in_img, executed, draw_roi=False)`
  把**已执行节点的检测结果**画好（**不画 ROI 辅助框**），经 `OVERLAY_PROVIDER` 交给节点；取不到就退回数据层。
  **默认选叠加**，因为纯处理链下两档**像素完全一样**（用例逐像素证过）⇒ 默认它不改变旧行为，却让检测内容能存下来；
- **录制生命周期**：第一帧自动开录（定尺寸/帧率）→ 每帧写一次 → **6 处收尾**（「停止」/ 播到末尾·关相机 / 换页 / 删节点 / 关程序 / 关换相机）；
  **尺寸或输出参数变化 ⇒ 收尾旧文件 + 另开新文件**；**0 帧 ⇒ 删掉空文件**；
- **视频格式**：实测本机 `mp4v / XVID / MJPG` 都能写能读；**不做 H.264**（依赖本机没有的 openh264 dll，会打印加载失败，靠回退侥幸能写）。
  体积实测（1280×720 / 25fps）：mp4v ≈ 7.7 MB/分钟、XVID ≈ 7.9、MJPG ≈ 23；
- **帧率口径**：手填 > 来源（视频源读到的 / 相机兜 30）> 25，按"**每写一帧算一帧**"；
- **失败一律不弹窗**（目录为空 / 写不进去 / 编码器不支持），只写执行日志。

### 4.10 设备与播放

- **相机**：主窗口统一开关（`_open_camera_device` / `_release_camera_device`），相机源节点通过注入的取帧器**复用**；
  **一轮执行只读一次相机**（否则"画面"和"算法算的那张"不是同一帧）；`「停止」= 暂停、`删除` = 关相机`（用户拍板）。
- **视频**：`SourceOps` 各自缓存 `VideoCapture`（按 `(路径, mtime, 大小)`），与主窗口播放**各读各的、不抢读指针**；
  `run_video()` **只读当前帧、不前进**，前进由主窗口 `_advance_video_cursor()` 统一做（同一轮多节点共用同一帧）。
- **自动出画面**：视频与相机**共用同一个 QTimer**；视频间隔 = `1000/fps`（坏值兜 25，夹到 5~1000ms），相机按 30ms。

| 无撤销/重做、无快捷键 | —— | 靠"保存项目"留档 |
